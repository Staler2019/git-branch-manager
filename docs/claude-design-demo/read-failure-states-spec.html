先更正我上一則的說法。我問「面板內一行失敗訊息」時，說 spec「沒有規定面板內的樣子」。spec 沒有規定面板內的樣子 這是錯的：P19 樣板規則 5 寫明「例外狀態用面板內 banner，不用 dialog、不用 toast。」所以你的裁定對 12 個 GbmPanelTabShell 面板有 spec 依據；其餘畫面（compare 頁、History 明細、Working copy diff、對話框）不是 P19 面板，仍然沒有出處，列在第 4 節另外裁定。

4. 裁定（2026-11-15）

使用者裁定：「1,2 用a」「3照你說的做ok」，以及「4照你說，2照你原本提案」。

  1. 面板失敗狀態用 A（GbmWarningBanner，放在 shell 的 banner 插槽，加一顆 Open log）。
  2. 非 P19 畫面照原提案：compare 頁與 History 明細用 A，放在窗格頂端；WC diff 沿用窗格現有的那一行；對話框用 warn 欄位，預覽失敗時停用 Delete。
  3. 兩則 banner 同時出現時，只顯示失敗那一則。
  4. 舊內容屬於別的對象（U／C 類）就清空；屬於同一個對象（R 類清單）就保留並加 banner。

裁定前的提問（保留原文）

  1. 面板失敗狀態用哪個元件：A（現有 GbmWarningBanner，跨整個面板）或 B（P19 mock 的凹陷小卡）。我建議 A：worktrees 已在用、同一面板裡不會出現兩種例外樣式，而且規則 5 的文字寫的是 banner。
  2. 非 P19 畫面（compare 頁、History 明細、Working copy diff 窗格、Clean 對話框、Repository settings）：spec 沒有出處。我的提案是：compare 頁與 History 明細用同一個 A 元件放在窗格頂端；WC diff 沿用窗格現有的「refused」那一行；對話框用 dlgFields 的 warn 欄位，並在預覽失敗時停用 Delete。每一項都是推斷，請逐項同意或否決。
  3. 兩個 banner 同時出現：worktrees 刷新失敗時，又剛好有路徑失效的項目。我建議失敗那一則在上、只顯示一則，失效那一則等下次成功刷新再出現。推斷。
  4. 失敗後畫面上要不要保留舊內容：U／C 類的舊內容可能屬於另一個對象（blame 是別的檔案），我建議清空。R 類的舊清單仍然是同一個對象，我建議保留並加 banner。推斷。

5. Inferred（沒有出處、由我推斷的部分）

  • 失敗 banner 放「Open log」：P19 的 banner 沒有按鈕；按鈕放在 banner 裡有 P07 mock 的先例，「Open log」這個動作來自 P15 錯誤視窗與 P10 10-3「status bar 常駐可點的摘要」。把兩者組合起來是推斷。
  • B 的小卡裡放按鈕、按鈕垂直置中、文字 flex:1：callout 5 沒有按鈕。
  • 文案壓成一行、超出時以 … 截斷：P15 的寫法是為錯誤視窗寫的（標題 + 一到兩句），濃縮成一行是我的組合。文案用中文句子，git 名詞與原始訊息保持英文，跟隨 worktrees banner 現有的寫法。
  • B 放在工具列下方、上下 8px、左右 10px 外距：mock 把它畫在明細欄裡。
  • 面板高度（150／104px）只是畫圖用；警告圖示的路徑取自 lucide 的 alert-triangle，spec 原始碼讀不到路徑資料。

7. 不需要畫面裁定的 native 部分

每個 C／U 類 read 的失敗回覆改成帶上成功回覆同一個 key（path／oid／ref／requestId），Dart 才能把失敗對應到畫面；匯出函式在交出前丟例外時也走同一個失敗回覆；CallbackRegistry::emit 在 malloc 失敗時（缺口 3b）要有替代的通知。這屬於跨 FFI 的 wire 變更，計畫要先經 plan-verifier。畫面已裁定，下一步依本頁寫實作計畫。
