Working Copy Layout

The two file lists stop sitting side by side and stack down the left; the diff takes the whole right. Written before any code changes, because this one overturns two rows of the spec's own SPLITTERS table and that should be a decision, not a diff.

01

The complaint, and what actually causes it

「目前左右不好看檔案內容」 — the file content is the thing that needs width, and today it is the only thing that never gets any.

The Working Copy is split top/bottom: file lists above, diff below. The file lists are then split left/right into Unstaged and Staged. So the diff gets 54% of the height and 100% of a width it did not need to share — while two columns of file paths, which are short, get the full width above it. Then the diff pane splits itself left/right again for 2 file mode, and the code that actually has to be read ends up in a box roughly a quarter of the window.

Rotating both dividers fixes it without adding a single pane: file paths are short and stack happily; a diff is tall and narrow-hostile. The stack gives the diff a full-height column and every pixel the window gains from then on.

Not a conformance fix

Everything on this page is a deviation the user asked for, in the same standing as the Working Copy's removed checkboxes. Section 06 quotes exactly what it overrules, so a later audit reads it as ratified rather than as drift to be repaired.

03

The one open question: what the left column's width does

Both options are draggable and both remember where you left them. They differ in one thing only — what happens to the extra width when the window grows.

The numbers below are not window widths. The Working Copy is the trailing pane of splitterMainSidebar, so it never sees the whole window: a 1280 window hands it 1280 − 250 (sidebar) − 1 (divider) = 1029, and 1920 hands it 1669. Every figure is that number, split. An earlier draft of this page computed from the raw window width and overstated both diff panes by ~250px.

The file column grows with the window too. Keeps wc.diff's existing flex behaviour and only re-proportions it — closer to what the spec's SPLITTERS row describes, which is a ratio and not an extent.

Needs a ruling

Recommendation: Option A. The complaint is that file content has no width; A is the only one of the two where widening the window is a cure. A 500px-wide column of file paths at 1920 is space spent on strings that are ~30 characters long. Concretely, at 1920 the diff gets 1408 under A and 1168 under B — 240px, or about 20 more columns of code, for a file list nobody asked to be wider.

The counter-argument for B is honest and worth stating: it is nearer the spec's own row (a ratio), and it needs no invented pixel default — A's 260 and 180 have no source at all (section 04). If you pick A, those two numbers are yours to set; the ones drawn above are a proposal.

How narrow the column may get, either way

Both options need a floor, and the floor is a real arithmetic question because the Unstaged pane carries the drop hint and the Staged pane does not — while GbmSplitPane applies one shared minExtent to both panes.

05

The drop hint has to change, and has nothing to quote

「拖曳檔案到右欄 = stage」 — once Staged is below rather than beside, 右欄 is simply false. A hint pointing the wrong way is worse than no hint: it is a control that lies.

#CandidateArgument
C1拖曳檔案到下欄 = stage Recommended. One character changes — 右 → 下. Keeps the spec's own sentence shape, its =, and its word 欄, so the deviation is as small as a deviation can be while still being true.
C2拖曳檔案到下方 = stage 下方 reads slightly more natural than 下欄 for something stacked, but abandons the spec's noun. Marginally better Chinese, marginally further from the source.
C3往下拖 = stage · 往上拖 = unstage Says both directions, which the current hint never did — the Staged pane has no hint of its own and unstaging is undiscoverable. Honest, and the biggest departure: new information, not a corrected word.
Needs a ruling

C1 unless you want the unstage direction spelled out, in which case C3. The mockups in section 02 and 03 are drawn with C1.

06

What this overrules, quoted

Two rows of spec page 09's SPLITTERS table, both of which today's code matches exactly. dir names the divider line's own orientation.

RowSpec, verbatimAfter this round
wc.columns { id: 'wc.columns', where: 'Unstaged ↔ Staged', dir: '垂直', def: '1 : 1', min: '200px', note: '' } line becomes horizontal; ratio 1 : 1 kept; min re-derived as a height
wc.diff { id: 'wc.diff', where: '檔案區 ↔ Diff', dir: '水平', def: '46 / 54', min: '150px', note: '' } line becomes vertical; def/min replaced per section 03

Both storage keys must be re-keyed rather than reused. That is not a preference: [FLU-splitpane-axis-change] states that changing a pane's axis obliges a decision about the stored value, and only ratio mode survives one. A re-key orphans the old panelLayout.wc.* entries — they read-miss and fall back to the default, which is a lost width, never a wrong one.

P03's own mockup draws today's arrangement too. It is overruled by the same ruling and for the same reason; it is not quoted separately because it says nothing the two rows above do not already say in numbers.

Records to correct when this lands
  • docs/reports/spec-conformance-matrix.md — both rows currently read 符合. Struck and rewritten in place as a ratified deviation, or the next audit repairs this layout back to the old one.
  • [STRUCT-working-copy] — 「Below the columns, the diff area…」 stops being true.
  • [STRUCT-two-column-switches] — the Working Copy row's default flips to unified.
  • splitterWcDiffSides's doc comment — 「nested inside splitterWcDiff's 54% share」 stops being true.

08

Acceptance

  • A layout test asserts Unstaged's rect is above Staged's and the files column's right edge is at or before the diff's left edge — both against the neighbour, so the test cannot pass by matching a constant that also moved.
  • A test asserts the commit box is still the last child and still spans the full width. This is the only mechanical statement of 「位置不變」.
  • The stacked column at its minExtent throws no overflow. RenderFlex reports main-axis overflow only, so this test is on the vertical axis by construction.
  • Pumping the diff pane with no interaction shows one column. Tapping 2 file shows two, left unstaged and right staged — the existing dx assertion, kept, now behind a tap.
  • Dragging a row from Unstaged downward onto Staged stages it, and upward unstages — with the empty-column placeholder still inside the DragTarget's builder, so a first-ever file can still be dropped on.
  • flutter analyze at zero and dart format clean; the five device-tier candidates run one at a time, each with a control run on the parent commit.
