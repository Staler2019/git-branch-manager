Working Copy Layout

兩個檔案清單不再左右並排，改成堆疊在左側；diff 拿走整個右半邊。這一頁寫在動任何程式碼之前， 因為它推翻了 spec 自己 SPLITTERS 表裡的兩列 —— 那應該是一個決定，不是一份 diff。

01

抱怨是什麼，真正的成因又是什麼

「目前左右不好看檔案內容」 —— 檔案內容才是需要寬度的那個東西， 而今天它是唯一永遠拿不到寬度的東西。

Working Copy 是上下切的：檔案清單在上、diff 在下。檔案清單接著又左右切成 Unstaged 與 Staged。 所以 diff 拿到的是高度的 54%，加上一個它根本不需要分給別人的 100% 寬度—— 而兩欄本來就很短的檔案路徑，在它上面佔滿整個寬度。接著 diff 面板為了 2 file 模式再左右切一次，真正需要被讀的程式碼最後被塞進大約視窗四分之一寬的盒子裡。

把兩條分隔線各轉 90° 就解決了，而且不用多加任何一個 pane：檔案路徑短，堆疊起來完全沒問題； diff 是又高又怕窄的東西。堆疊之後 diff 拿到一整欄的高度，以及視窗從此之後長出來的每一個像素。

這不是 conformance 修正

這一頁上的每一件事都是使用者要求的偏離，與 Working Copy 拿掉 checkbox 同一個位階。 第 06 節逐字引用了它推翻的東西，所以之後的稽核會把它讀成「已裁定」，而不是「待修的 drift」。

已裁定 —— 「tree 一起修」

這不是改版面造成的；它在今天的 app 上、在任何寬度下都成立 —— 所以修它本來不在這一輪的範圍內。是使用者明確把它拉進來的。它以 W10 出貨， 自己一個可以單獨 revert 的 commit。

List 模式不受影響 —— 平鋪清單沒有父資料夾可以扣掉，所以完整路徑留在那裡，那是對的。

刻意沒有動的東西

  • commit box —— 還是最下面那一條、滿寬、一樣 200px、一樣的欄位、一樣 132px 的按鈕欄。 「位置不變」照字面實作。
  • 衝突區塊，有的時候一樣釘在所有東西上面。
  • 檔案換邊還是用拖的；一樣沒有 checkbox。只有方向從往旁邊變成往下。
  • 2 file / unified 切換鈕，以及 2 file 模式裡面 那條分隔線。只有預選哪一個變了。
  • list / tree 切換鈕 —— 一樣的位置（Unstaged 的標題列，兩欄共用一個）， 一樣是與 History、Compare、衝突視窗共享的 app 層級偏好。有疑問的只有葉節點那一列的 文字，而且只在 tree 模式下。
03

唯一一個待決的問題：左欄的寬度怎麼走

兩個方案都可以拖，也都記得你把它放在哪裡。它們只差一件事 —— 視窗變大時，多出來的寬度歸誰。

下面的數字不是視窗寬度。Working Copy 是 splitterMainSidebar 的後面那個 pane， 所以它從來看不到整個視窗：1280 的視窗給它 1280 − 250（側邊欄）− 1（分隔線）= 1029，1920 給它 1669。 每一個數字都是這個數字再切開。這一頁早先的草稿是從原始視窗寬度算的，兩個 diff pane 都多估了約 250px。

05

Drop hint 非改不可，而且沒有東西可以引用

「拖曳檔案到右欄 = stage」 —— 一旦 Staged 變成在下面而不是在旁邊， 右欄 就是假的。一個指錯方向的提示比沒有提示更糟：那是一個會說謊的控制項。

#候選論點
C1拖曳檔案到下欄 = stage 建議這個。只改一個字 —— 右 → 下。保留 spec 自己的句型、它的 =、它的欄字，所以在「還是真的」的前提下，偏離已經小到不能再小。
C2拖曳檔案到下方 = stage 下方 reads slightly more natural than 下欄 for something stacked, but abandons the spec's noun. Marginally better Chinese, marginally further from the source.
C3往下拖 = stage · 往上拖 = unstage Says both directions, which the current hint never did — the Staged pane has no hint of its own and unstaging is undiscoverable. Honest, and the biggest departure: new information, not a corrected word.
已裁定 —— C1

「拖曳檔案到下欄 = stage」。動一個字， 右 → 下；句型、= 與欄這個名詞全部維持 spec 的。第 02、03 節的 mockup 已經照這樣畫了。 Staged 那個 pane 仍然沒有自己的提示 —— 會補一個的是候選 C3，而它沒有被選上， 所以 unstage 的可發現性維持今天的樣子。

06

stage/unstage 的 scope 卡片，從來沒有被寫下來過

「這部分之前只有 code 修改，沒有設計在 spec 上」 —— 沒錯，而且比聽起來更糟。 設計是存在的，而且是你的；不存在的是 docs/ 底下任何一頁記錄它。 這個 repo 裡唯一的痕跡，是 Dart 註解裡的一組 CSS class 名稱。

來源是 Diff Scope Studies 的 變體 B —— claude.ai/code/artifact/bd3d9fdf-18a4-473a-95b3-27aa34966361。它在 docs/rules/ops-spec-reading.md 裡以 [SPEC-demo-dom-is-the-spec] 被引用， 但網址被截成 bd3d9fdf-…，所以那條「要讀 DOM」的規則光靠 repo 是遵守不了的。 這一節把它的 CSS 和 DOM 都抓回來了。它的 token 名稱與 app 的一對一對應 —— --space-1..4 是 4/8/12/16、--radius-sm/md 是 4/6、 --text-xs/sm 是 11/12.5、--row-h-compact 是 26 —— 所以下面每一個數字都可以直接跟真的常數比對，中間不需要換算。

已裁定 —— 「照建議」，六題全部
  • S3 虛線 —— 建議採用。虛線不是裝飾：它是把 臨時選取的一次性區塊， 跟會留著的實線邊卡片區分開來的東西。今天兩個都是實線，只有顏色不同。

  • S6 +N −M —— 建議保留 badge，而這是唯一一處建議 不照設計走、而且理由是設計本身而不是一致性的地方。變體 B 寫的是 .variant-B-plus { color: var(--diff-add-strong) }，而 --diff-add-strong 是淡背景色 —— light 是 #bfe9cd、 dark 是 #173e24。把它當文字色畫在標頭自己的 panel-raised 底上， 在這個 app 出貨的主題裡就是 #161b22 上面放 #173e24：幾乎讀不到。 上面那張 specimen 就是照它寫的畫的，所以左邊那些數字看起來像不見了。 一致性也指向同一邊 —— 這個 pane 旁邊的兩個檔案清單，畫同一件事用的就是 GbmBadge。

驗收

  • 一個版面測試斷言 Unstaged 的 rect 在 Staged 上方，以及檔案欄的右緣不超過 diff 的左緣 —— 兩個都是對著鄰居斷言，所以測試不可能靠對上一個同時也移動了的常數而過關。
  • 一個測試斷言 commit box 仍然是最後一個子節點、仍然滿版寬。這是「位置不變」唯一一個機械化的說法。
  • 堆疊欄在 minExtent 時不丟溢出。RenderFlex 只回報主軸溢出，所以這個測試在結構上就是落在垂直軸上。
  • 不做任何互動就 pump diff pane，看到的是一欄。點 2 file 之後是兩欄，左 unstaged、右 staged —— 既有的 dx 斷言留著，只是現在放在一次點擊後面。
  • 把一列從 Unstaged 往下拖到 Staged 會 stage，往上拖會 unstage —— 而且空欄的 placeholder 仍然在 DragTarget 的 builder 裡面，所以第一個檔案仍然放得進去。
  • Tree 模式的葉節點列畫的是它在父資料夾之下的那一段，不是完整路徑 —— 斷言方式是在 tree 模式下 pump 那個 board、讀畫出來的東西，跟當初找到這個缺陷的方式一樣。List 模式仍然畫完整路徑，在同一個測試裡斷言，這樣一個把兩邊都改掉的「修法」會失敗。
  • §06 採納的每一個屬性都用 identity 斷言，絕不用「沒有丟例外」—— 邊框的 BorderSide.style、chip 的顏色對上 colors.warning、hover 色對上它的 token。一個只檢查樹還建得起來的卡片 hover 測試，就是 [FLU-hand-rolled-inkwell-hover] 記下的那種失敗。
  • flutter analyze 歸零、dart format 乾淨；五個裝置層候選一次跑一個，每一個都在父 commit 上跑一次對照組。

None of the three readings won: U1 was ruled on a fourth — order by change region, and never merge two directions into one scope. It keeps block 1's warning intact instead of trading it away, which is why it beat the option I recommended.

what makes region ordering computable

The two diffs look incomparable and are not: they share the index as a coordinate space. The unstaged diff is index → work tree, so its old side is the index; the staged diff is HEAD → index, so its new side is the index. One ruler, both sides, and no new git call.

A region's place on that ruler is read per line, not per hunk — every DiffLine already carries oldLine and newLine (parsed_diff.dart:39,40), so a scope's index range is the min and max of the index-side number over the lines it spans: oldLine for an unstaged scope, newLine for a staged one. oldStart/newStart would only locate the hunk, and the ruling's unit is the region inside it.

Two things this deliberately does not do. It never claims two rows are the same row — only that one region precedes another, which is what keeps block 1's warning honoured. And it never merges: two regions that land on the same index lines stay two scopes, adjacent, one per direction.

The one gap: a scope made entirely of lines absent from the index side (a pure insertion in the work tree) has no index number of its own, and has to be anchored to the nearest line that does. And an untracked file's unstaged diff is --no-index /dev/null → file, which has no index side at all — but such a file has no staged side to order against until it is staged, so the case never arises.

U1What one list is ordered by — 使用者裁定 「我要對齊的不是行號，是 git 判斷出的區域變更，每個區塊會是一個 scope，然後 unstage, stage 必定是不同 scope」

The alignment unit is the change region, not the line. git already decides where a change region begins and ends, and splitHunkIntoScopes() already turns each one into exactly one DiffScope — so the unit the ruling names is a unit the code already has. The list is a sequence of regions in file order; each region is one card; each card is one direction.

And a region is never mixed. A staged scope and an unstaged scope are always two scopes, never merged into one card — which is what makes the button on every card answerable: one press, one direction, one thing git can actually do.

This settles the contradiction rather than picking a side of it. 變體 B block 1 forbids 硬對齊 because lining two different diffs' rows up asserts they are the same line.
