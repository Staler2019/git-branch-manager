01

抱怨是什麼，真正的成因又是什麼

「目前左右不好看檔案內容」 —— 檔案內容才是需要寬度的那個東西， 而今天它是唯一永遠拿不到寬度的東西。

Working Copy 是上下切的：檔案清單在上、diff 在下。檔案清單接著又左右切成 Unstaged 與 Staged。 所以 diff 拿到的是高度的 54%，加上一個它根本不需要分給別人的 100% 寬度—— 而兩欄本來就很短的檔案路徑，在它上面佔滿整個寬度。接著 diff 面板為了 2 file 模式再左右切一次，真正需要被讀的程式碼最後被塞進大約視窗四分之一寬的盒子裡。

把兩條分隔線各轉 90° 就解決了，而且不用多加任何一個 pane：檔案路徑短，堆疊起來完全沒問題； diff 是又高又怕窄的東西。堆疊之後 diff 拿到一整欄的高度，以及視窗從此之後長出來的每一個像素。

這不是 conformance 修正

這一頁上的每一件事都是使用者要求的偏離，與 Working Copy 拿掉 checkbox 同一個位階。 第 06 節逐字引用了它推翻的東西，所以之後的稽核會把它讀成「已裁定」，而不是「待修的 drift」。

驗收

  • 一個測試斷言 commit box 仍然是最後一個子節點、仍然滿版寬。這是「位置不變」唯一一個機械化的說法。
  • 堆疊欄在 minExtent 時不丟溢出。RenderFlex 只回報主軸溢出，所以這個測試在結構上就是落在垂直軸上。

為什麼「依區域排序」算得出來

兩份 diff 看起來無從比較，其實不然：它們共用 index 這個座標系。 unstaged diff 是 index → 工作區，所以它的舊側就是 index； staged diff 是 HEAD → index，所以它的新側就是 index。 一把尺、兩邊都量得到，而且不需要新的 git 呼叫。

一個區域在那把尺上的位置是逐行讀的，不是逐 hunk —— 每一個 DiffLine 本來就帶著 oldLine 與 newLine （parsed_diff.dart:39,40），所以一個 scope 的 index 區間， 就是它涵蓋的那些行的 index 側行號的最小值與最大值：unstaged scope 取 oldLine， staged scope 取 newLine。oldStart/newStart 只能定位到整個 hunk，而裁定的單位是 hunk 裡面的區域。

有兩件事它刻意不做。它從不宣稱兩列是同一列 —— 只宣稱某個區域排在另一個之前，這就是 block 1 的警告能被守住的原因。 它也從不合併：兩個落在同樣 index 行上的區域仍然是兩個 scope，相鄰，一個方向一個。

唯一的缺口：一個完全由 index 側不存在的行組成的 scope（工作區裡的純新增） 沒有自己的 index 行號，必須錨定到最近一個有的行上。而未追蹤檔案的 unstaged diff 是 --no-index /dev/null → file，根本沒有 index 側 —— 但這種檔案在被 stage 之前也沒有 staged 側可以排序，所以這個情況不會發生。

#題目裁定，以及為什麼
U1一份清單依什麼排序 —— 使用者裁定 「我要對齊的不是行號，是 git 判斷出的區域變更，每個區塊會是一個 scope，然後 unstage, stage 必定是不同 scope」

對齊的單位是變更區域，不是行。git 早就決定了一個變更區域從哪裡開始、到哪裡結束， 而 splitHunkIntoScopes() 早就把每一個區域變成剛好一個 DiffScope —— 所以裁定講的那個單位，程式碼裡已經有了。這份清單就是一串依檔案順序排列的區域； 一個區域一張卡片；一張卡片一個方向。

而且一個區域絕不混方向。staged scope 與 unstaged scope 永遠是兩個 scope， 絕不併成同一張卡片 —— 這就是每張卡片上那顆按鈕答得出來的原因： 按一下、一個方向、一件 git 真的做得到的事。

這是把矛盾解掉，不是選邊站。變體 B block 1 禁止 硬對齊，是因為把兩份不同 diff 的列對齊， 等於宣稱它們是同一行。而排序區域只宣稱某個區域在檔案裡排在另一個之前， 這件事在兩份 diff 本來就共用的 index 座標裡是真的。 所以 (b) 的錯覺被避開了，也不必退回 (a) 的分組 —— 那會把對同樣幾行的兩次編輯，用整個檔案的長度隔開。

#狀態項目改幾處是什麼
C1doneindex 座標改成兩段1 + 測試 IndexPosition 從一個 int 變成 ({int line, int offset})。offset 0 表示這一列就是 index 的第 line 行，offset 1 表示它夾在第 line 行與下一行之間。一段式的座標讓未追蹤檔案的每一列都回報同一個數字，於是「照區域排序」退化成「照來源的先後」。這是三個缺陷裡最容易漏的一個——它要等另外兩個修好才看得見。
C2donegap 規則接受硬邊界1 + 測試 splitHunkIntoScopes 多一個 barriers，被指名的未變更行不可以被吞進 scope。規則寫成「不可以吞掉邊界」而不是「碰到邊界就結束 scope」——它只作用在同一側兩個變更中間的未變更行，所以所有單一來源的 fixture 一個字都不用改。同一顆 commit 裡加上 changedIndexLines（誰是邊界）與 barrierLineIndices（翻成那個 hunk 自己的列號）。
C3doneunified 接上邊界1 + 測試 每一個來源拿到其他來源改到的 index 行當邊界，切出來就是 git 看到的三個區域：Stage 2 lines / Unstage 1 line / Stage 2 lines。2 file 只有一個來源，邊界集合是空的，所以這一項在那個模式裡結構上就是惰性的，不需要旗標。
C4done同一個 index 行不畫兩次（裁定 B）1 + 測試 「b」——一側畫成未變更、另一側畫成變更的那一行，在合併清單裡只畫一次。hunkSegments 多一個 hiddenLines，而關鍵不是「跳過那一列」，是把那一段未變更的跑馬燈從那裡切成兩段；只跳過不切，上下兩段 context 會悄悄併成同一個區塊。
C5done標題列的計數也用同一組邊界3 + 測試 收尾時才發現的第四個缺陷。「N 未暫存 · M 已暫存」有自己的 DiffScopeCache，呼叫時不帶方向也不帶邊界——所以在這個案例上，卡片是三張，標題列寫的是 1 未暫存 · 1 已暫存。修法不是在 pane 裡再算一次（那就是這個缺陷本身的形狀），而是把 ScopedDiffView 私有的 memo 抽成純層的 DiffBarrierMemo，兩邊共用（[CULT-single-source-of-truth]）。原本那段 doc comment 保證「the chip cannot say a number the list disagrees with」，就地劃掉改寫。
C6done記錄4 兩條新 pin：[FLU-index-position-is-two-part] 與 [FLU-other-side-changes-are-barriers]。[FLU-merged-diff-keys-by-source] 裡那句「fallback 是 hunk 自己的 start」就地更正成 start - 1 配 offset。[STRUCT-working-copy] 的切 scope 那一句補上邊界。ledger 追加一段。
