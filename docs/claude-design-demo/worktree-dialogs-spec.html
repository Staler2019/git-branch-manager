Scope, and where it stops

The twelve management panels do ship CJK labels and were reviewed without objection, so “this app is English” was never an inferable rule — it was put to the user rather than assumed. The ruling is scoped to dialogs. The panels are out of scope and this spec does not touch them.

Theme check

Every colour in the specimen resolves from a token, and all three palettes are defined independently — so the three buttons above are a real test, not a tint. Two things this audit caught:

A defect, now fixed. --surface-sunken was referenced by five rules (the read-only field, the list field, the picker list, the warning, and the shortcut chip) and defined in none of the three palettes. An undefined custom property makes the whole declaration invalid at computed-value time, so those backgrounds were silently transparent in every theme — which is precisely why the warning looked flat. It is now #eef0f2 / #010409 / #f5f6f8, taken from tokens-reference.md. Seven tokens that nothing referenced were removed at the same time, so the block states only what it governs.

The shell now follows P6's full-size mock, not its prose

P6 states the shell twice and the two disagree: the prose says 「標題列（18px semibold）+ 內容區（16px padding）」, while the page's own full-size dialog mock draws 13px and 14px. 使用者裁定：照 spec 用 13 — so the mock is the source, and it is taken whole rather than cherry-picked, because a geometry half from each is a third thing neither says.

Three consequences worth naming. The shell ground becomes --surface-panel-raised, so the --surface-panel fields now read as sunken into a raised panel rather than floating on the same tone — which is what .gbm-input's own background was always for. The action row moves out of the body into its own padded region, which is why it now has real weight under the rule. And the title bar needs no background of its own: the border-bottom is the whole separator, exactly as P6 draws it.

GbmDialogShell currently implements the prose (textLg 18, space4 16), so this is a real change to the shared shell, not just to this dialog — it is G6 and G7 in the work list.

03

Language, per element

使用者裁定：「現在都是中文的，那就改成中文」。 The spec does not simply “use Chinese” — it splits by element type, consistently, across all 26 dialogs it draws. Counted from DLGS in spec_logic.js:

ElementEnglishChineseRule
Dialog title260Always English. Checkout, New branch, Merge into current, Clone repository…
Primary button260Always English. Create branch, Stash 9 files, Prune 5 refs, Delete on origin…
Field label347Chinese, except proper nouns — the three English ones are URL and Remote×2.
Option text4081Chinese. The 40 English are data — release/0.5, origin/main, paths and hashes — not copy.
Hint013Always Chinese.
What this makes cheap

Titles and buttons are already correct — the app writes those in English and so does the spec. So the change is confined to labels, options, hints, warnings and notes.

And for 26 of the 30 dialogs the spec supplies the exact wording, so most of this is transcription rather than translation. new_branch's start-point label is 「從哪裡分出」, not a phrase anyone has to invent — which incidentally settles the START POINT question from an earlier draft of this page.

Where the spec writes it for us

Checkout, Merge into current, Rebase onto, New branch, Clone repository, Stash changes, Force push, Delete remote branch, Prune remote branches, Restore file ×2, Discard changes, Reset branch, Cherry-pick, Create tag, Clean untracked files, Undo last operation, Sign in to origin, Checkout blocked, Deleted branch recovery, New repository, Open file at this revision, Save this revision as, Pull, Set upstream, Pull blocked.

The four with no spec entry — Add Worktree, Lock Worktree, Remove Worktree and Preferences — get copy composed in the same voice. That voice keeps git's own vocabulary in English inline (「先 stash，切完不自動還原」, 「建立後直接 checkout」), so checkout, stash, worktree and --force stay as they are.

05

Explicitly not changing

A redesign is read as licence unless the licence has edges. These are the edges.

  • GbmDialogShell width (480) and the title 'Add Worktree'.
  • The radio / picker / text-field / checkbox structure and its order.
  • Icons.folder_open_outlined on the Browse button.
  • Every OutlineInputBorder(), isDense, contentPadding and GbmSpacing value already in the file.
  • Submit-enablement logic, the path-occupancy check, and the browse handler.
  • The twelve management panels' CJK labels — out of scope, see section 01.

Acceptance

  • Re-running section 01's sweep returns 0 CJK literals under features/dialogs/. Corrected in place. That sentence was written while the ruling was 「dialog 全英文」, and it survived the reversal to 「現在都是中文的，那就改成中文」 unchanged — so this page's own acceptance check demanded the opposite of its own section 03. A zero-CJK sweep is now a failing result for every element type except titles and primary buttons.
  • The sweep that replaces it is per element, not per file, because section 03's rule is: every title: and primary-button label under features/dialogs/ is ASCII, and every field label, hint, warning and non-data option is not. One grep cannot express that, so it is two.
  • A widget test pins 來源, 分支 and both radio labels, so the added group label cannot be quietly dropped later. Source, Branch — the English names were this page's earlier draft and are corrected here rather than left to be read as the target.
  • Existing add_worktree / lock_worktree / remove_worktree tests move to the new strings in the same commit. A finder still matching a Chinese label means a string was missed. Inverted by the same reversal: a finder still matching an English field label, hint or warning is the miss. A finder matching an English title or primary button is correct and must stay.
  • integration_test/ is grepped for every changed label and for the GbmActionId / GbmPanelKind that reach these surfaces — per [TEST-grep-misses-intent-driven-device-tests], a device test can arrive through an intent without naming any label.
